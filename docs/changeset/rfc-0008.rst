Create: agent-exec
~~~~~~~~~~~~~~~~~~

:Status: Contract
:Date: 2026-09-30

Scope and authority
^^^^^^^^^^^^^^^^^^^

``agent-exec`` is the library crate ``shared/crates/agent-exec`` that runs one
headless invocation of a backend CLI for the servers of this workspace. It owns
binary lookup, argv construction, spawning, output capture, cancellation,
failure classification and the model fallback loop, and it returns one record
per run with the backend's token usage normalized. ``harness-log``, the library
crate ``shared/crates/harness-log``, locates a backend's session files and
parses token usage from a backend's own output. The public items of the two
crates are authoritative for names and types; this document is authoritative
for the behavior behind them.

A server decides what to run and what to do with the result: aside composes a
prompt and renders a reply, dispatch keeps its run store and its watchdogs. The
crates write no file and no store of their own.

Definitions and model
^^^^^^^^^^^^^^^^^^^^^

Backend
"""""""

``Backend`` is ``Codex``, ``Claude`` or ``Opencode``. Each names its binary
(``codex``, ``claude``, ``opencode``), an install hint and a ``--version``
probe. Codex and Claude are spawned as processes with the prompt on stdin;
Opencode is driven through ``opencode serve`` on a free localhost port and its
HTTP session API.

Sandbox
"""""""

``Sandbox`` is ``ReadOnly``, ``WorkspaceWrite`` or ``DangerFullAccess``. Codex
receives it as ``-s``; Claude as a permission mode (``plan``; ``acceptEdits``
with ``Bash`` allowed; ``--dangerously-skip-permissions``); Opencode as its
permission rules. The ceiling that refuses ``DangerFullAccess`` belongs to the
server.

Isolation
"""""""""

``Isolation`` states how a spawned backend is kept from reaching back into the
server that spawned it. For Codex: ``IgnoreUserConfig`` (``exec
--ignore-user-config``, no MCP server at all) or ``DisableMcpServer(name)``
(``-c mcp_servers.<name>.enabled=false`` before ``exec``, every other server
kept). For Claude: ``SafeMode { tools }`` (``--safe-mode
--no-session-persistence --permission-mode plan --tools <list>``) or
``Permissions`` (the sandbox mapping alone). Every spawned process also
carries the re-entry marker (see Re-entry).

OutputMode
""""""""""

``OutputMode`` is ``Text`` (the backend's final message on stdout),
``Json`` (Claude ``--output-format json``) or ``JsonStream`` (Codex ``exec
--json``). ``Json`` and ``JsonStream`` are what usage is parsed from; ``Text``
yields a record whose ``usage`` is ``None`` unless the caller later attaches
usage parsed from a session file.

RunSpec
"""""""

One invocation: ``backend``, ``prompt``, ``working_dir`` (optional; set as the
process directory and, for Codex, ``-C``), ``sandbox``, ``isolation``,
``output_mode``, ``model``, ``reasoning_effort``, ``resume_session``,
``pin_session`` (Claude ``--session-id``; with ``resume_session`` it adds
``--fork-session``), ``skip_git_repo_check`` (Codex), ``stdout_cap`` and
``stderr_cap`` in bytes, ``env`` (extra variables), ``reentry`` (the marker
name and ceiling) and ``guard`` (whether the process runs under the
parent-death guard).

RunEvent
""""""""

What a run reports while it lasts: ``Started { pid, argv, backend_version,
session_id, port }`` once the process or the Opencode server is up;
``Progress(line)`` for each normalized JSONL event the Opencode runner
produces (``session_meta``, ``user_message``, ``agent_message``,
``reasoning``, ``tool_call``, ``tool_result``, ``task_started``,
``task_complete``, ``error``); ``Finished(RunRecord)``. The caller receives
events through a channel it supplies.

RunRecord
"""""""""

The serializable result of one attempt: ``backend``, ``argv``, ``model``,
``reasoning_effort``, ``started_at``, ``wall_ms``, ``exit_code``,
``success``, ``cancelled``, ``stdout`` and ``stderr`` as captured within
their caps with ``stdout_total`` and the two truncation flags,
``final_text`` (the backend's last assistant message when the output mode
gives one), ``session_id`` when the backend reports one,
``backend_version``, and ``usage: Option<Usage>``.

Usage
"""""

Token counts of one run in disjoint buckets, each ``Option<u64>``:
``input_uncached``, ``cache_read``, ``cache_write_5m``, ``cache_write_1h``,
``output`` and ``reasoning``. ``reasoning`` is the part of ``output`` spent on
reasoning or thinking and is never added to ``output``. A count the source
does not report is ``None``; zero means the source reported zero.
``usage_source`` names where the counts came from: ``codex_json_stream``,
``codex_rollout``, ``claude_json_result`` or ``opencode_message``. When a run
has several turns or iterations, the buckets are sums over them.

Re-entry
""""""""

A server names an environment variable and a ceiling (aside:
``ASIDE_REENTRY_DEPTH``, ceiling 1; dispatch: ``DISPATCH_REENTRY_DEPTH``,
ceiling 1). Every spawned process carries the variable at the server's depth
plus one; a server refuses a request when its own depth is at or above its
ceiling. An unset or empty value is depth 0; a malformed or non-Unicode value
is past every ceiling.

Guard
"""""

On Linux and macOS a guarded process is started through a hidden
re-invocation of the server binary that leads the process group and kills the
group when the server dies, mirroring the backend's exit status; on Windows
the process is placed in a Job Object that kills on close. The server calls
``guard::maybe_run_guard()`` before anything else in ``main`` so that the
re-invocation never starts a runtime or opens a store.

Contract
^^^^^^^^

Functions
"""""""""

- ``which(binary)`` returns the first executable file named ``binary``, or
  ``binary.exe`` on Windows, on ``PATH``.
- ``version(backend)`` runs ``<binary> --version`` with the re-entry marker
  stamped and returns its first non-empty output, else ``None``.
- ``install_hint(backend)`` returns one line telling how to install the CLI.
- ``run(spec, events, ct)`` performs one attempt and returns ``Outcome``:
  ``Record(RunRecord)`` when the process was spawned and awaited (success or
  failure), ``NotFound { binary, hint }`` when ``which`` finds nothing,
  ``Spawn(message)`` when the process could not be started or its stdin
  written, ``Cancelled`` when the token fired.
- ``run_with_fallback(spec, chain, events, ct)`` runs ``spec.model`` then
  each model of ``chain`` in order while the previous attempt's failure text
  classifies as retry-worthy and an attempt remains; it returns the final
  ``Outcome``, the model that produced it and the list of discarded attempts
  (model, kind, first 200 characters of the failure text).
- ``errkind::classify(text)`` returns ``BackendErrorKind``: ``RateLimited``,
  ``QuotaOrBilling``, ``ModelUnavailable``, ``AuthOrPermission`` or ``Other``;
  the first three are retry-worthy.
- ``reentry::depth(name)``, ``reentry::stamp(command, name)`` and
  ``reentry::refused(name, ceiling)`` implement Re-entry.
- ``guard::maybe_run_guard()`` and ``guard::wrap(command)`` implement Guard.

Argv
""""

Codex, in this order: ``-C <working_dir>`` when set; ``-s <sandbox>``;
``-a never``; ``-m <model>`` when set; ``-c model_reasoning_effort=<effort>``
when set; ``-c mcp_servers.<name>.enabled=false`` for
``DisableMcpServer``; ``exec``; ``--ignore-user-config`` for
``IgnoreUserConfig``; ``resume <session>`` when resuming;
``--skip-git-repo-check`` when set; ``--json`` for ``JsonStream``. No
positional prompt: the prompt is written to stdin and stdin is closed.

Claude, in this order: ``-p``; the isolation and sandbox flags (``--safe-mode
--no-session-persistence --permission-mode plan --tools <list>`` for
``SafeMode``; ``--permission-mode plan``, ``--permission-mode acceptEdits
--allowedTools Bash`` or ``--dangerously-skip-permissions`` for
``Permissions`` by sandbox); ``--input-format text``; ``--output-format
text`` or ``json``; ``--model <model>`` when set; ``--effort <effort>`` when
set; ``--resume <session> --fork-session`` when resuming; ``--session-id
<id>`` when pinned. The prompt is written to stdin.

Opencode: ``opencode serve --hostname 127.0.0.1 --port <free port>`` in
``working_dir``; a session is created, resumed when ``resume_session`` is
set, and the prompt is posted with the provider and model parsed from
``model`` as ``<provider>/<model>``; permission rules follow the sandbox. The
server process is killed when the run ends.

Capture and failure text
""""""""""""""""""""""""

stdout and stderr are read concurrently and kept up to their caps; overflow
is drained and discarded and the record marks the truncation. The failure
text used for classification and shown to the user is stderr followed by
stdout, because Claude prints the discriminating error on stdout and exits
non-zero with only warnings on stderr.

Usage mapping
"""""""""""""

``harness-log`` exports one parser per source, each returning
``Option<Usage>``:

- ``codex_json_stream(text)``: over every ``turn.completed`` event,
  ``input_uncached = max(0, input_tokens - cached_input_tokens) -
  cache_write_input_tokens`` (floored at zero), ``cache_read =
  cached_input_tokens``, ``cache_write_5m = cache_write_input_tokens``,
  ``output = output_tokens``, ``reasoning = reasoning_output_tokens``.
- ``codex_rollout(path)``: the same buckets from ``token_count`` events,
  each delta taken from ``last_token_usage`` when present, else from the
  change in ``total_token_usage``.
- ``claude_json_result(text)``: from the result's ``usage``,
  ``input_uncached = input_tokens``, ``cache_read =
  cache_read_input_tokens``, ``cache_write_5m =
  cache_creation.ephemeral_5m_input_tokens``, ``cache_write_1h =
  cache_creation.ephemeral_1h_input_tokens``, ``output = output_tokens``,
  ``reasoning = output_tokens_details.thinking_tokens``; when
  ``usage.iterations`` is present the buckets are summed over it.
- ``opencode_message(value)``: ``input_uncached = tokens.input``,
  ``cache_read = tokens.cache.read``, ``cache_write_5m = tokens.cache.write``,
  ``output = tokens.output``, ``reasoning = tokens.reasoning``.

A field absent from the source leaves its bucket ``None``; a parser never
substitutes zero.

Session location
""""""""""""""""

``harness-log`` keeps the location functions the servers use today: the
Codex home and rollout listing, session metadata, the newest interactive
rollout for a directory, the rollout for a nonce or a session id, and the
Claude session file for a session id.

Errors and edge cases
^^^^^^^^^^^^^^^^^^^^^

- A missing binary is ``NotFound`` with the install hint; ``which`` does not
  find ``.cmd`` shims on Windows.
- Cancellation kills the process group (or the Job Object) and returns
  ``Cancelled``; no record is produced for that attempt.
- A fallback attempt after a ``Cancelled`` outcome is not made.
- A ``NotFound`` or ``Spawn`` outcome is not retry-worthy.
- An Opencode server that does not answer within its startup timeout is
  killed and reported as ``Spawn``.
- A record whose output mode gives no parseable usage carries ``usage:
  None``; a server may attach usage parsed from a session file afterwards.

Ownership and ordering
^^^^^^^^^^^^^^^^^^^^^^

- The server owns the ``RunSpec``: its isolation, sandbox, caps, output mode
  and re-entry marker are the server's policy; the crate applies them.
- The crate owns argv construction: a server never appends to the argv it
  gets back.
- The server owns everything written to disk or a store; the crate reports
  through ``RunEvent`` and its return value only.
- ``guard::maybe_run_guard()`` runs first in every server ``main``.
- Fallback attempts are made in chain order and each attempt is reported as
  its own ``Started`` event.

Compatibility
^^^^^^^^^^^^^

The crates are workspace-internal and versioned with the workspace. Within a
kit major version a ``RunRecord`` or ``Usage`` field is added, never removed
or renamed, so a record written by one server is readable by another; a new
``usage_source`` value is added when a new source is parsed.

Conformance
^^^^^^^^^^^

- argv tests per backend and isolation assert the flag set and order above.
- Spawn, capture, truncation and cancellation tests run against a stub
  executable placed on ``PATH``.
- Each usage parser has a synthetic fixture and a test that an absent field
  yields ``None``.
- Guard tests run on Linux and macOS; the Job Object is exercised on
  Windows CI.
- ``cargo test``, ``clippy -D warnings`` and ``fmt --check`` pass for the
  workspace on Linux, macOS and Windows.

Sources
^^^^^^^

``shared/rules/core/``
  The kernel (the articles, in six parts) and the execution, delegation and
  git rule files, which hold only what the articles do not imply.

``shared/rules/mcp/``
  When to consult (aside) and when to dispatch.

``shared/workflows/palette/``
  The palette rule, the palette skills, and the document templates, which are
  also the schema the palette server checks against.

``shared/workflows/memory/``
  The memory-triage skill.

``shared/prefs/``
  The templates of the user-owned prefs files.

``adapters/<harness>/``
  ``tokens.sed`` (render-time values, including the kit version),
  ``inserts/*.md`` (harness-specific text for each insert marker) and, for
  Codex and Kimi, ``surface.md`` (how that harness loads the rules and reaches
  the servers).

``shared/crates/``
  The Rust libraries the servers share: agent-exec (one headless backend
  invocation, from binary lookup to a run record with normalized token
  usage) and harness-log (session location and usage parsing for each
  backend's own output).

``shared/mcp-servers/``
  The Rust MCP servers: aside (consultation, on codex and claude), dispatch
  (external execution, on codex, claude and opencode) and palette (document
  reads, checks and writes). aside and dispatch run their backends through
  agent-exec and differ in the parameters they pass.

``shared/setup/``
  The Rust installer, ``slate-setup``.

``tooling/``
  ``render-kit.sh`` (renders a kit), ``validate.sh`` (checks sources and
  renders), ``install-mcp.sh`` (builds the servers and registers them through
  the installer), ``slate-version`` (the slate release a kit's binaries come
  from), and ``kit-scripts/`` (the entry-point and maintainer templates).

Replace: Settings
~~~~~~~~~~~~~~~~~

Settings
^^^^^^^^

Keys for ``--set`` are ``<file>.<key>``. Each key is stored under the heading
named after it below; a template that lacks a heading makes install fail with
a message naming the file and the heading. A blank value is written ``****``.

- aside: ``level`` Level; ``backend`` Backend; ``<backend>.model``
  "<Backend> model"; ``<backend>.effort`` "<Backend> reasoning effort";
  ``<backend>.fallback`` "<Backend> model fallback", for Codex and Claude.
- dispatch: ``level`` Level; ``backend`` Backend; ``model`` Model; ``effort``
  Reasoning effort; ``fallback`` Model fallback.
- subagent: ``level`` Level; ``model`` Default model; ``effort`` Reasoning
  effort.
- git: ``signing`` Commit signing; ``attribution`` Model attribution;
  ``commit-format`` Commit message format; ``pr-body`` PR body format;
  ``branch-naming`` Branch naming.
- comment: ``headers`` File headers; ``language`` Comment language;
  ``doc-comments`` Doc comments.

The allowed values:

aside
  ``level`` (``on-request``, ``suggest``, ``auto``; default ``suggest``);
  ``backend`` (``codex``, ``claude``); per backend ``model``, ``effort``
  (``low``, ``medium``, ``high``, ``xhigh``, ``max``, or blank) and
  ``fallback`` (a comma-separated model list, or blank), as
  ``aside.codex.model`` and so on. Only the chosen backend's values are asked.
  A file that still carries the settings of an earlier backend installs; the
  installer reports them in one warning line and treats them, and a
  ``backend`` value naming that backend, as blank.

dispatch
  ``level`` (default ``suggest``); ``backend`` (``codex``, ``opencode``,
  ``claude``); ``model``; ``effort`` (``low``, ``medium``, ``high``, ``xhigh``,
  or blank); ``fallback``.

subagent
  ``level`` (default ``suggest``); ``model`` (blank: the harness default;
  validated per spec/installer.rst *Native configuration*); ``effort`` (Codex
  and Kimi only).

git
  ``signing`` (``default``, ``no-gpg-sign``, ``unset``); ``attribution``
  (``on``, ``off``, ``unset``); ``commit-format`` (``conventional``,
  ``repository``, free text, ``unset``); ``pr-body`` (``summary-test-plan``,
  ``repository``, free text, ``unset``); ``branch-naming`` (``descriptive``,
  ``repository``, free text, ``unset``). ``unset`` means the agent asks the
  user when it first needs the value and records the answer.

comment
  ``headers`` (``repository``, ``structured``, free text); ``language``
  (``repository``, ``english``, ``korean``, free text); ``doc-comments``
  (``repository``, ``public-api``, free text).
